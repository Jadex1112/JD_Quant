# Chapter 21 – Order Management

## 21.1 Purpose

The Order Management System (OMS) is the single authority for order state (CON-003). It accepts order intents from strategies, users, and API clients; validates them; obtains a pre-trade risk decision; hands accepted orders to the Execution Engine; applies execution reports to maintain order state; and publishes order and fill events to downstream consumers.

## 21.2 Scope and Actors

### In Scope

- Order intent acceptance and validation
- Client order identifier generation and idempotency
- Order lifecycle state management
- Order modification and cancellation
- Fill processing and fee capture
- Parent/child and contingent order relationships (OCO, bracket)
- Order and fill queries, blotter
- Order reconciliation with venues

### Actors

| Actor | Interaction |
|---|---|
| Strategy Engine | Submits order intents on behalf of deployments |
| Quantitative Trader | Submits manual orders, modifies, cancels |
| API Client | Submits orders programmatically |
| RMS | Provides pre-trade decisions |
| EMS | Routes orders and returns execution reports |
| PME / Position Engine | Consumes fills |

## 21.4 Order State Model

| State | Description | Terminal |
|---|---|---|
| CREATED | Intent accepted and validated by OMS | No |
| PENDING_RISK | Awaiting RMS decision | No |
| RISK_REJECTED | Rejected by RMS | Yes |
| PENDING_SUBMIT | Approved, queued for EMS | No |
| SUBMITTED | Sent to venue, not yet acknowledged | No |
| OPEN | Acknowledged by venue, working, no fills | No |
| PARTIALLY_FILLED | Working with one or more fills | No |
| PENDING_CANCEL | Cancel requested, not confirmed | No |
| PENDING_REPLACE | Modify requested, not confirmed | No |
| FILLED | Fully filled | Yes |
| CANCELED | Canceled (possibly after partial fills) | Yes |
| REJECTED | Rejected by venue or EMS validation | Yes |
| EXPIRED | Expired by time in force | Yes |
| UNKNOWN | State cannot be determined (timeout, disconnect) | No |
| TRIGGER_PENDING | Stop or emulated conditional order waiting for trigger | No |

Transition table:

| From | To | Trigger |
|---|---|---|
| CREATED | PENDING_RISK | Validation passed |
| CREATED | REJECTED | Validation failed |
| PENDING_RISK | PENDING_SUBMIT | RMS approve |
| PENDING_RISK | RISK_REJECTED | RMS reject |
| PENDING_RISK | TRIGGER_PENDING | RMS approve for emulated conditional order |
| TRIGGER_PENDING | PENDING_RISK | Trigger condition met (re-check risk) |
| TRIGGER_PENDING | CANCELED | Cancel request |
| PENDING_SUBMIT | SUBMITTED | EMS sends to venue |
| PENDING_SUBMIT | CANCELED | Cancel before send |
| SUBMITTED | OPEN | Venue ack |
| SUBMITTED | PARTIALLY_FILLED / FILLED | Fill before ack |
| SUBMITTED | REJECTED | Venue reject |
| SUBMITTED | UNKNOWN | Ack timeout or disconnect |
| OPEN | PARTIALLY_FILLED | Partial fill |
| OPEN, PARTIALLY_FILLED | FILLED | Final fill |
| OPEN, PARTIALLY_FILLED | PENDING_CANCEL | Cancel request |
| OPEN, PARTIALLY_FILLED | PENDING_REPLACE | Modify request |
| OPEN, PARTIALLY_FILLED | EXPIRED | Venue expiry / TIF |
| OPEN, PARTIALLY_FILLED | CANCELED | Unsolicited venue cancel |
| PENDING_CANCEL | CANCELED | Cancel confirmed |
| PENDING_CANCEL | FILLED / PARTIALLY_FILLED | Fill racing cancel |
| PENDING_CANCEL | prior state | Cancel rejected |
| PENDING_REPLACE | OPEN / PARTIALLY_FILLED | Modify confirmed (with new price/quantity) or rejected (old values retained) |
| PENDING_REPLACE | FILLED | Fill racing modify |
| UNKNOWN | any non-UNKNOWN state | Resolved by status query or reconciliation |

Any fill received for an order in a terminal state other than FILLED shall be applied (quantities corrected), the anomaly logged, and an `order.state.anomaly` event published; the venue is the source of truth (CON-042).

## 21.5 Functional Requirements – Order Intake and Validation

| ID | Requirement | Pri | Ver |
|---|---|---|---|
| FR-21001 | The system shall accept order intents from strategies, the user interface, and the public API through a single intake interface. | M | T |
| FR-21002 | The system shall generate a client order identifier unique per account for every order; client-supplied identifiers shall be accepted only through the API and shall be checked for uniqueness. | M | T |
| FR-21003 | The system shall return the existing order, without creating a new one, when an intent is received with an idempotency key already used by the same submitter within 24 hours (CON-008). | M | T |
| FR-21004 | The system shall validate required fields per order type as specified in 21.3.1 and reject violations with `ORDER_VALIDATION_FAILED` listing each violated field. | M | T |
| FR-21005 | The system shall validate quantity against lot size, minimum quantity, maximum quantity, and minimum notional of the instrument; prices against tick size and venue price bands (CON-040). | M | T |
| FR-21006 | The system shall optionally round prices to the nearest valid tick (passive direction: down for BUY, up for SELL) and quantities down to the lot size when the submitter requests rounding; otherwise it shall reject misaligned values. | M | T |
| FR-21007 | The system shall reject orders for instruments whose status is not ACTIVE. | M | T |
| FR-21008 | The system shall reject orders whose account lacks the permission required by the instrument and order flags (for example reduce_only on a spot account, SHORT without short permission). | M | T |
| FR-21009 | The system shall reject orders when the eligibility conditions of BR-19-02 are not met, returning the specific blocking condition. | M | T |
| FR-21010 | The system shall reject post_only orders whose limit price would cross the current best opposite price when the venue does not enforce post_only natively. | S | T |
| FR-21011 | The system shall validate orders in no more than 200 μs p99 excluding RMS time. | M | T |

## 21.6 Functional Requirements – Risk Integration and Submission

| ID | Requirement | Pri | Ver |
|---|---|---|---|
| FR-21020 | The system shall obtain an RMS pre-trade decision for every order before transitioning to PENDING_SUBMIT (CON-004). | M | T |
| FR-21021 | The system shall reject the order with `RISK_UNAVAILABLE` if no RMS decision is received within the configured timeout (default 50 ms); orders shall never be submitted by default on RMS timeout. | M | T |
| FR-21022 | The system shall record the RMS decision identifier on the order. | M | T |
| FR-21023 | The system shall hand approved orders to the EMS in the order approved, per account and instrument. | M | T |
| FR-21024 | The system shall allow order modification (price, quantity, or both) for OPEN and PARTIALLY_FILLED orders; modifications that increase risk (larger quantity, more aggressive price) shall require a new RMS decision. | M | T |
| FR-21025 | The system shall implement modification as native replace where supported by the venue, and as cancel-then-new otherwise, preventing the combined order from exceeding the original intent quantity minus filled quantity. | M | T |
| FR-21026 | The system shall allow cancellation of any non-terminal order and shall support bulk cancellation by account, deployment, instrument, side, or all. | M | T |
| FR-21027 | The system shall treat cancellation requests idempotently: repeated cancel requests for the same order produce no additional venue requests while PENDING_CANCEL. | M | T |

## 21.7 Functional Requirements – Execution Reports and Fills

| ID | Requirement | Pri | Ver |
|---|---|---|---|
| FR-21040 | The system shall apply execution reports from the EMS to order state according to the transition table in 21.4. | M | T |
| FR-21041 | The system shall de-duplicate fills using (venue, instrument, venue_trade_id); duplicate fills shall be ignored and counted. | M | T |
| FR-21042 | The system shall update filled_quantity and average_fill_price atomically with fill persistence. | M | T |
| FR-21043 | The system shall detect overfills (filled_quantity > quantity), accept the venue values, flag the order, and raise a Critical alert. | M | T |
| FR-21044 | The system shall capture fees per fill, including negative fees (rebates), in the fee currency reported by the venue; where the venue reports no fee the system shall estimate it from the account's fee schedule and mark it estimated. | M | T |
| FR-21045 | The system shall publish `order.fill` for every accepted fill within 1 ms p99 of processing. | M | T |
| FR-21046 | The system shall transition SUBMITTED orders to UNKNOWN if no acknowledgment is received within the configured timeout (default 5 s), and instruct the EMS to resolve their state by client order identifier query before any resubmission. | M | T |
| FR-21047 | The system shall never automatically resubmit an order in UNKNOWN state; resubmission requires resolution to REJECTED or confirmation that the venue has no record of the client order identifier. | M | T |

## 21.10 Business Rules

| ID | Rule |
|---|---|
| BR-21-01 | average_fill_price = Σ(fill.price × fill.quantity) / Σ(fill.quantity). |
| BR-21-02 | remaining_quantity = quantity − filled_quantity; a modification may not set quantity below filled_quantity. |
| BR-21-03 | An order is "working" in states SUBMITTED, OPEN, PARTIALLY_FILLED, PENDING_CANCEL, PENDING_REPLACE, UNKNOWN, TRIGGER_PENDING. Working orders count toward open-order limits and risk exposure. |
| BR-21-04 | Notional = quantity × price × contract_multiplier, where price is limit price, or the current reference price (BR-20-04) for market orders. |
| BR-21-05 | Order records are never deleted; terminal orders remain queryable for the retention period. |
| BR-21-06 | For the same order, execution reports are applied in venue sequence order where the venue provides sequence numbers; otherwise in exchange timestamp order. |

## 21.14 Acceptance Criteria

| ID | Criterion | Traces To |
|---|---|---|
| AC-21001 | Given the same idempotency key submitted twice within 24 h, then exactly one order exists and both calls return its identifier. | FR-21003 |
| AC-21002 | Given RMS does not respond within 50 ms, then the order is rejected with RISK_UNAVAILABLE and no venue request is made. | FR-21021 |
| AC-21003 | Given a venue ack timeout, then the order becomes UNKNOWN, a status query is issued, and no second order with a new client order identifier is sent until resolution. | FR-21046, FR-21047 |
| AC-21004 | Given the same fill delivered twice by stream and REST reconciliation, then filled_quantity reflects it once. | FR-21041 |
| AC-21005 | Given a bracket order whose entry fills 60%, then take-profit and stop-loss orders are active for 60% of the quantity. | FR-21061 |
| AC-21006 | Given an order open at the venue but missing in the OMS after a restart, then reconciliation imports it as EXTERNAL and raises a warning. | FR-21083, FR-21084 |
